# ISUCON14 (ISURIDE) 計測改善ループ

## 大原則

**計測なき改善は禁止。1改善 = 1コミット = 1ベンチ。**

ベンチは初期化＋60秒＋検証で**約90秒**。まとめて入れる理由はない。
まとめた瞬間に、下がったときどれが原因か分からなくなる。

## 1サイクル

```sh
make bench NOTE="何を確かめたいか"      # measurements/<ts>/ と scores/log.md に記録
# measurements/<ts>/score.json → alp.txt → slow.txt → cpu-*.txt の順に読む
# 実装 → git commit（本文に「根拠: measurements/<ts>/xxx の数字」を書く）
make deploy && make bench
git add measurements scores docs && git commit -m "bench: <score> <何の計測か>"
```

## ISURIDE のスコアの構造を忘れない

スコアは「リクエストをさばいた数」ではなく**ライドの距離と完了数**。

```
スコア ≒ Σ(マッチ位置→乗車位置の距離)×0.1 + Σ(乗車位置→目的地の距離) + 完了数×5
```

- ライドが増える条件 = **ユーザーが増える** = 満足度が高い（評判による新規登録・招待）。
- 満足度の要素（アプリケーションマニュアル記載）:
  1. 配車を依頼してから椅子が割り当てられるまでの時間（→ **マッチング間隔・処理速度**）
  2. 割り当てられた椅子が乗車位置に早く着きそうか（→ **近い椅子・速い椅子を選ぶ**）
  3. 割り当てから乗車までの時間（→ 通知の遅延、座標更新の応答速度）
  4. 乗車から目的地までの時間（→ 椅子の速度、座標更新の応答速度）
- ベンチの出力 `score.json` の **`dissatisfied`（matching / pickup / ride の不満率）**が
  そのままこの4要素の成績表。alp より先に見る。
- 椅子は「座標更新リクエストが成功したことを確認するまで移動しない」。
  → `POST /api/chair/coordinate` が遅いと**椅子が物理的に遅くなる**＝ride の不満に直結する。

## 判断を間違えやすい点

### 1. スコアのブレを先に測る

負荷はユーザー満足度で自己増殖するので、同一コードでも数%〜十数%ぶれうる。
改善の効果がブレ幅より小さいときは、**同じコードでもう1回回して**から判断する。
ブレ幅は `scores/log.md` にメモしておく。

### 2. 「速く返す」と「良い結果を返す」は別の軸

マッチングのアルゴリズムを変えるとリクエスト処理量は同じでもスコアが大きく動く。
逆に、処理を速くしても不満率が下がらなければスコアは伸びない。
**変更のたびに不満率3種を前回と並べて見る。**

### 3. 反映遅延と整合性（WARN が200件で FAIL）

- nearby-chairs は座標送信から3秒以内、owner/chairs の total_distance も3秒猶予。
- 通知は**すべての状態遷移を順序通り**返す。キャッシュやSSE化で1つでも飛ばすと
  クリティカルエラー（即FAIL）。
- 決済: 支払い漏れ・誤った支払いは即FAIL。リトライと `Idempotency-Key` の扱いは慎重に。

**WARN / ERROR の件数が前回より増えた変更は、スコアが上がっていても原因を特定するまで進まない。**

### 4. SQLを変えたら EXPLAIN ANALYZE を見る

```sh
make explain SQL="SELECT ..."
```

`Table scan on` / `Sort:` / actual rows が返す行数より桁違いに大きい → 直っていない。

### 5. プロファイルの割合はマシン全体の割合ではない

先に `cpu-<host>.txt`（pidstat）でプロセス別CPUを見る。c5.large は 200% が上限。
mysqld が支配しているのにアプリのアルゴリズムを磨いても効かない（逆も同じ）。

### 6. 状態をメモリに持つなら、再起動と initialize で復元できること

追試は「3台を再起動 → 負荷走行」。アプリ内キャッシュは
**起動時と `POST /api/initialize` で DB から作り直す**。DBを正とし、書き込みはDBに入れる。

### 7. サーバーの状態を変えたら

- ミドルウェアを再起動したらアプリも再起動する（死んだ接続を掴む）。`make deploy` がやる。
- スキーマ変更は `webapp/sql/1-schema.sql`（または initialize が流すSQL）に入れる。
  **initialize のたびにテーブルは作り直される**ので、ssh で ALTER しても次のベンチで消える。

### 8. 観測を原因と取り違えない

「今その現象が出ていない」は「その現象が起きない」ことの証拠にならない。
自分の設定（例: `retry_after_ms`）が作り出した観測結果を、ベンチマーカーの性質と読み違えない。
**入れて測る。**

### 変更を入れたら、1回目の結果を見てから次を回す

ハンガリアン法の初版は panic してマッチングが止まり、3回続けて FAIL した（1回目で止めるべきだった）。
行列の向きを入れ替える経路がテストされていなかった。データの形が変わる分岐（依頼 < 空き椅子 など）は両方テストする。

### プロファイル

`./tools/analyze/pprof.sh isucon14-3 30 out.pprof` をベンチ中（開始から45秒後くらい）に叩く。
アプリは 127.0.0.1:6060 で pprof を待ち受けている。reflect の sort.Slice が上位に来たら slices.SortFunc に。

### メモリと DB の二重管理で踏んだ罠

- **メモリを先に進めるなら、外部に見える通知は DB のコミット後に出す。**
  マッチングを「メモリ→SSE通知→DB」にしたら、DB の UPDATE がプール待ちで遅れる間に椅子がライドを
  最後まで進め、遅れて来た UPDATE が updated_at（完了日時）を上書きした。
- **応答をDB書き込みで待たせない。** 「メモリで送信済み → 同期UPDATE → 応答」だと、UPDATE が遅い間
  「サーバーは送信済み・クライアントは未受信」になり、別APIの判定とずれる。
- 初期データは `INSERT INTO t VALUES (...)`（列名なし）なので、列は投入後に `ALTER TABLE` で足す。

## ベンチマーカーはブラックボックス

ソースを読んで挙動を先回りしない。判断材料は外から観測できるものだけ
（スコア、不満率、WARN、新規登録数、alp、自分のサーバーのログ）。

## Red Flags — 手を止めて計測に戻る

- 「N+1が見えているから計測は飛ばす」→ 次の一手が見えなくなる
- 「時間が無いから複数まとめてベンチする」→ ベンチは90秒
- 「このクエリは明らかに速いはず」→ EXPLAIN ANALYZE を見ていないなら分かっていない
- 「スコアは下がったが理論的には良いはず」→ ブレ幅を確認して、それでも下がっていれば revert
- 「WARN は数件だから許容」→ 負荷が増えると比例して増え、200件でFAIL
- 「ベンチが頭打ちだからアプリをもっと速くする」→ 先に不満率とベンチ機のCPUを見る

## 締め

1. `make restart-test` — 3台再起動後もベンチが通るか（追試と同じ）
2. `make measure-off` — `long_query_time=0` のまま最終計測しない
3. 新規の大きい変更をしない
